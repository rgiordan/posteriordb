# Project handoff: paragami, modelgami and posteriordb_jax

This file is for Claude (or anyone) picking up this work cold. It records the
goal, the design decisions Ryan has made, the current state of the code, what
is still open, and how the work was organized. Written 2026-10-13, at commit
`4d710cf` on branch `modelgami-first-draft`, when the project moved to a new
account. Ryan's coding conventions are in
[`CODING_PREFERENCES.md`](CODING_PREFERENCES.md) and apply to everything here.

## Goal

A standardized, JAX-based Python interface to support flexible statistics
research, with a focus on Bayesian methods.

In Ryan's words: the goal is to reduce the modeling boilerplate he has to
write when running statistical experiments for methodological research. A
model he comes across should be implemented once, in a common interface, and
then reused, so that a new methodological idea can be tried quickly on a large
number of models.

So two things must stay cheap:

1. **Writing a model:** a parameter pattern plus a couple of ordinary JAX
   functions over dicts of arrays.
2. **Running one method across many models:** one loop, or one Slurm
   submission, with no per-model glue.

## Repository and setup

- Repository: `github.com/rgiordan/posteriordb`, a fork of posteriordb (the
  Stan model / data / reference-draw database).
- Branch: `modelgami-first-draft`, open as **draft PR #1**
  (https://github.com/rgiordan/posteriordb/pull/1) against `master`.
- All three packages are developed together under `python/`, as separately
  installable packages, and will be split into their own repos once they're
  ready (Ryan's decision). None imports a sibling by relative path, so
  splitting means moving directories.

```
python/
  paragami/          parameter folding / flattening / transforms (JAX only)
  modelgami/         the model interface (depends on paragami)
  posteriordb_jax/   posteriordb models as modelgami Models, plus a Slurm runner
  notebooks/         demo notebooks, setup_venv.sh, requirements.txt, make_notebooks.py
  .gitignore         Python cruft (checkpoints, __pycache__, venvs, Stan builds, ...)
```

Dependency chain: `paragami <- modelgami <- posteriordb_jax`.

### Environment

- `python/notebooks/setup_venv.sh` creates `python/notebooks/.venv`, installs
  `requirements.txt` (editable installs of the three packages plus jax,
  numpyro, blackjax, arviz, jupyter) and prints the command to register the
  `modelgami` Jupyter kernel. The notebooks default to that kernel.
- Tests: `pytest python/paragami/tests`, `pytest python/modelgami/tests`,
  `pytest python/posteriordb_jax/tests`. Tests that compile Stan are marked
  `stan` (deselect with `-m 'not stan'`). The full posteriordb_jax suite is
  slow (BridgeStan compiles every model); give it a long timeout.
- Optional extras: `paragami[arviz]`; `modelgami[arviz,numpyro,stan]`;
  `posteriordb_jax[stan,mcmc,legacy]`. `stan` means BridgeStan, `mcmc` means
  BlackJAX, `legacy` means TensorFlow Probability.
- **JAX versions:** current JAX works for everything except the legacy
  TFP-based translations (`posteriordb_jax.models`), because TFP 0.25 needs
  JAX <= 0.5. Earlier threads ran the tests on both JAX 0.5 and 0.11; TFP
  tests are skipped on the newer one.
- `posteriordb_jax` turns on `jax_enable_x64` on import, which the Stan
  comparisons need. paragami and modelgami don't force it.

### Notebooks (`python/notebooks/`)

1. `01_paragami`: paragami alone, including nested dicts, inferring a pattern
   from data and printing its code, the Stan/TFP bijector option, the
   validation switch, and ArviZ round trips.
2. `02_defining_a_model`: a robust regression defined with parameter dicts.
3. `03_sampling_with_blackjax`: free-space log joint, BlackJAX NUTS, draws
   folded into ArviZ (with single-observation log likelihoods for LOO);
   checked against the exact conjugate posterior.
4. `04_posteriordb_with_blackjax`: catalog models fitted with BlackJAX and
   compared with posteriordb's reference draws (means within ~0.04 sd).

The notebooks are generated by `make_notebooks.py` (cells only; execute them
separately, e.g. with `jupyter nbconvert --execute --inplace`). They are
committed with outputs so they read on GitHub. When the API changes, update
`make_notebooks.py`, regenerate and re-execute.

## paragami (`python/paragami`)

A JAX rewrite of Ryan's original autograd paragami
(https://github.com/rgiordan/paragami), started from the parameter handling
that already existed in posteriordb_jax. Pure JAX, no TFP dependency.

**Three states** (Ryan's naming, chosen to remove ambiguity about direction):
- **folded:** the original structure (dict of arrays, nested to any depth);
- **flat:** constrained and flattened to a vector;
- **free:** unconstrained and flattened to a vector.

There is deliberately no "folded and free" state.

**Naming rules:** conversions are `x_to_y` (`folded_to_flat`,
`flat_to_folded`, `folded_to_free`, `free_to_folded`), and keyword arguments
are prefixed `to_` / `from_` (`flatten(p, to_free=...)`,
`fold(x, from_free=...)`). There is no default for `to_free`/`from_free`; the
caller must always say which. Everything is snake_case except class names,
which stay CamelCase (Ryan confirmed). Functions and methods are verbs:
`get_free_length()`, `get_flat_names()`, `draw_random`, `make_empty`,
`to_dict`, `generate_code`, `make_unconstrained_pattern_like`.

**Contents:**
- Patterns: `NumericArrayPattern`, `NumericScalarPattern`,
  `NumericVectorPattern` (bounds, plus Stan's `offset`/`multiplier`),
  `OrderedVectorPattern`, `UnitVectorPattern`, `SimplexArrayPattern`,
  `StochasticMatrixPattern`, `SumToZeroVectorPattern`,
  `SumToZeroMatrixPattern`, `CholeskyCorrPattern`, `CholeskyCovPattern`,
  `CorrMatrixPattern`, `PSDSymmetricMatrixPattern`. Containers: `PatternDict`,
  `PatternArray`.
- Transforms match Stan's exactly by default. `bijector="tfp"` selects TFP's
  transform wherever the two differ (one-sided bounds, simplexes,
  covariance and correlation patterns). `test_against_stan_and_tfp.py` checks
  every transform against BridgeStan and TFP.
- `free_to_folded` only folds. The log determinant is computed only on
  request (`free_to_folded_log_abs_det`, or `free_to_folded_with_log_det` for
  both), because folding runs many times inside algorithms.
- Validation can be switched off for speed: `pattern.disable_validation()` /
  `enable_validation()`, and on a container this sets every child.
  `validate_folded` always checks.
- `function_input_<from>_to_<to>` and `function_output_<from>_to_<to>` change
  the representation a function takes or returns (these replace the original
  `FoldFunctionInput` etc.).
- `make_unconstrained_pattern_like(value, default_name=...)` builds an
  unconstrained pattern from a pytree the user already has (dict keys become
  names; lists/tuples become dict entries `name_0`, `name_1`, and fold back as
  dicts, which Ryan said is fine). Every pattern has `generate_code()`, which
  prints readable Python that recreates it, to paste and edit (e.g. add
  constraints). The type switch that used to do this was replaced by a method
  on each pattern, and `infer.py` was merged into `codegen.py`.
- ArviZ conversion lives in paragami (`arviz_io.py`, optional extra):
  `free_draws_to_arviz`, `folded_draws_to_arviz`, `arviz_to_free_draws`,
  `arviz_to_folded_draws`, and array-only helpers like
  `free_draws_to_folded`.

## modelgami (`python/modelgami`)

**Principles Ryan set:**
- Users write ordinary JAX Python. No custom modeling language.
- Separate log-density and sampling functions are the default. A NumPyro
  hook exists, but users are never forced to write models that way. (TFP can
  also do both from one spec, but that is the user's choice, not required.)
- Keep inheritance to a minimum while avoiding repeated code. Functionality
  that only applies to exchangeable models lives in exchangeable subclasses.
- Priors and likelihoods are the same kind of object: a data generating
  process (`DGP`).
- No capability flags: a missing method raises `NotImplementedError`.
- Generic operations are standalone functions the classes call.
- Defaults match the math: a log density evaluates, up to a constant, the
  density of the object being called with respect to the arguments passed.

**Current API** (`dgp.py`, `model.py`):

- `DGP(eval_log_density=None, draw=None)`: either may be missing. Each DGP
  takes **its own random value first**:
  - prior: `eval_log_density(params, hyper)`, `draw(key, hyper)`;
  - likelihood: `eval_log_density(data, params, hyper)`,
    `draw(key, data, params, hyper)` (the data act as a template:
    covariates are kept, drawn fields replaced).
  Can be built from functions or subclassed.
- `free_dgp(dgp, pattern)` / `folded_dgp(dgp, pattern)`: change a DGP's base
  measure between constrained and unconstrained space, with the log Jacobian
  in the log density. This is how the Jacobian enters (Ryan: unconstraining
  is converting a DGP from one base measure to another).
- `ExchangeableDGP(eval_log_density_one, draw_one)`: N observations,
  independent given params and hyper. Data are an array of data: every leaf
  has a leading axis of length N. Anything not per-observation goes in
  `hyper` (Ryan: in an exchangeable model all data are exchangeable;
  non-exchangeable data are hyperparameters or extra arguments). Adds
  `eval_log_density_singleobs`, weighted `eval_log_density(..., weights=)`,
  `select_subset`, `eval_log_density_subset` (scaled by N/len(idx) by
  default, for unbiased minibatches).
- `exchangeable_dgp_from_distributions(make_dists_one)`: optional shortcut
  where the user returns NumPyro/TFP distribution objects and gets both the
  log density and the sampler. Ryan wanted it kept **only for exchangeable
  models** and said he will probably tweak its semantics later.
- `Model(likelihood, prior=None, data=None, hyper=None, params_pattern=None, name=None)`:
  only combines prior and likelihood. `prior=None` is a flat prior.
  `params_pattern=None` infers one from a prior draw. Methods:
  `eval_log_prior`, `eval_log_lik`, `eval_log_joint`, `eval_free_log_joint`
  (free prior with Jacobian plus likelihood, the target for HMC/VI),
  `draw_prior`, `draw_data`, `draw_joint`, `draw_marginal_data`. Every method
  takes optional `data=` / `hyper=` that default to the model's own (Ryan
  preferred this over a `with_data` method).
- `ExchangeableModel(Model)`: requires an `ExchangeableDGP`. Adds `n_obs`,
  `eval_log_lik_singleobs`, weighted `eval_log_joint(..., weights=)`,
  `eval_log_joint_subset`, `draw_np_bootstrap_weights(key)` (which calls the
  standalone `mg.draw_np_bootstrap_weights(key, n_obs)`).
- Standalone: `count_obs`, `draw_np_bootstrap_weights`, `make_hvp`.
- Adapters: `from_numpyro(program, data, hyper, exchangeable=...)` and
  `from_bridgestan(stan_file, data)`, which returns a `StanModel` (joint
  density of free parameters only; Stan data are fixed at compile time, so no
  derivatives with respect to data). **Ryan said he will review the adapters
  later; they have not been reviewed against the latest redesign.**
- `testing.py`: contract checks and `assert_models_match`.
- Worked example: `modelgami/examples/conjugate_regression.py`, a conjugate
  multivariate normal Bayesian regression with unknown homoskedastic
  variance, tested against the closed-form posterior and marginal likelihood.

**Removed on Ryan's review** (don't reintroduce): the `_user` hook dict,
`capabilities` / `can_sample`, `with_data`, `_fold_data` and data patterns,
the duplicated parameter and validation sections on `Model`, `shared_data`,
`prior_dists`, `log_density_fn` (one method that did several jobs), and
`model.to_arviz` (call `pg.free_draws_to_arviz` directly).

Not yet done from the original plan: user-supplied validation hooks for data
and params (Ryan asked for optional validation early on; the first version
was removed as duplication during review, and paragami's `validate_folded`
plus the validation switch remain). PyMC and Nimble adapters were discussed
as future work.

## posteriordb_jax (`python/posteriordb_jax`)

- `catalog/`: one module per Stan model, each defining `eval_*` / `draw_*`
  functions and a `build(raw)` that returns a `Model` or `ExchangeableModel`.
  **143 of 147 posteriordb posteriors** (from 116 Stan models) are converted.
  The 4 missing are the ODE models (see Open items).
- `catalog.load(name)`, `catalog.list_models(exchangeable=...)`,
  `catalog.load_reference_draws(name)`, `catalog.find_module(name)`.
- Checks: every catalog model matches BridgeStan on log density and gradient,
  and on the Hessian except a few large models. Posteriors with reference
  draws have NUTS posterior means within ~0.08 reference sd. Documented
  tolerance exceptions are commented in `tests/test_catalog.py` (Stan's
  approximate `bernoulli_logit` gradient for |logit| > 20 in irt_2pl,
  hier_2pl and horseshoe; skipped Hessians for the largest models and
  GLMM_Poisson; dogs old-translation gradient; kronecker_gp, where Stan's own
  numbers are slightly inaccurate). The last full run: 695 tests plus 7 batch
  tests, all passing.
- Modeling choices: radon models treat each house as one exchangeable
  observation carrying its county index (could be switched to plain `Model`).
  garch11's dependent bound is a small custom pattern in that model's file,
  not a paragami feature.
- `batch/`: runs any analysis `analysis(entry, out_dir)` on every posterior,
  locally or as a Slurm array job (`python -m posteriordb_jax.batch
  submit|local|status|list ...`). Each posterior gets a `status.json`
  (done / failed / not applicable); resubmitting reruns only unfinished ones.
  Ready-made analyses: `run_mcmc` (BlackJAX NUTS) and `run_bootstrap_mcmc`
  (uses `mg.draw_np_bootstrap_weights` by default, or `draw_weights=f`).
  `examples/batch_analyses.py` shows custom ones. **Never tested on a real
  Slurm cluster**, only with a fake `sbatch`. MCMC chains start from random
  draws of the parameter pattern.
- Legacy: `models/`, `model.py`, `constraints.py`, `flatten.py`,
  `stan_bijectors.py` are the original TFP-based `StatisticalModel`
  translations. Every model has a catalog version; the old ones are only used
  by `test_matches_old_translation`. **Ryan chose to leave them as they are**
  (not delete, not rename), even though they still use noun method names.
- Older docs at the repo root (`CLAUDE_TASK.md`, `PLAN_posteriordb_jax.md`)
  describe the original TFP translation project and are historical.

## Open items and priorities

1. **ODE solver (open decision for Ryan).** lotka_volterra,
   one_comp_mm_elim_abs, sir and soil_incubation need an ODE solver. Options
   offered: diffrax as an optional `ode` extra (recommended: standard JAX ODE
   library, differentiable), skip them, or a hand-written fixed-step RK.
   Stan's solvers have ~1e-6 relative tolerance, so the match against
   BridgeStan will be to that tolerance.
2. **Adapter review.** Ryan said he'd review `from_numpyro`,
   `from_bridgestan` / `StanModel` and the distribution hook after the core
   redesign. They need to be checked against the conventions above.
3. **Distribution-hook semantics** (`exchangeable_dgp_from_distributions`):
   Ryan expects to tweak them.
4. **Slurm runner on a real cluster.** Untested outside a fake `sbatch`.
5. **Splitting priors from likelihoods** in more catalog models, so methods
   that need weights, subsets or a separate prior run on as many models as
   possible. Many already have a separate prior, and 46 of the 128 catalog
   modules build an `ExchangeableModel`; check each module.
6. **Eventually:** split the three packages into their own repositories. The
   name `paragami` is taken on PyPI by the autograd version; the plan was to
   release the JAX version as paragami 1.0 from `rgiordan/paragami`. Nothing
   is published yet. Then mark PR #1 ready and merge.
7. Before relying on results for research, Ryan should read paragami's
   transforms and log-det Jacobian code himself; a subtle bug there would
   bias every model (the tests against Stan and TFP are the main safeguard).

## How the work was organized (and how Ryan likes to work)

- The old project used one coordinating Claude plus one thread per area:
  modelgami interface, paragami, posteriordb conversion, and coding
  preferences. Threads all pushed to `modelgami-first-draft`, pulled with
  rebase before each push, and edited only the files they owned. After any
  push that changed a package's public API, the owner sent a rename list to
  the threads that depend on it (paragami -> modelgami and posteriordb;
  modelgami -> posteriordb). Keep this discipline if work runs in parallel
  again.
- Ryan reviews by reading code and leaving a batch of notes. When he says he
  is making notes, don't change code until he says he's done, but answer his
  questions as he asks them. He often clarifies in several short follow-up
  messages; read them together before acting.
- He wants a reasonable default picked and stated, rather than work parked on
  questions. Ask him only about choices that change his goal or can't be
  undone, one short question with options and a recommendation.
- Report results with what was checked (tests run, comparisons made).
- Ryan's coding conventions were also set as project instructions in the old
  project; `CODING_PREFERENCES.md` is the full version and should become the
  new project's instructions (or a saved skill). A skill version,
  `ryan-coding-style`, was proposed in the old account.
